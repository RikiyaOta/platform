# 設計判断

## 1. platform とプロジェクトの2層に分ける

- **決定**: アカウント共有のものとプロジェクトの土台は platform に、アプリ固有のリソースは各プロジェクトに置く。
- **理由**: プロジェクトごとにトークンを手動で発行し、tfstate 用バケットを手動で作っていた手間をなくしたい。全体像も把握しやすくしたい。一方で、コードと一緒に変わるリソースはアプリの近くにある方が扱いやすい。

## 2. Terraform を使い続け、トークンが state に残ることは受け入れる

- **決定**: OpenTofu（state を暗号化できる）には移行しない。発行したトークンの値が state に平文で入ることは受け入れ、state の置き場所を守る。
- **理由**: Terraform を使い続けたい。企業でも、state に秘密が入ることを受け入れて置き場所を厳重に守る運用は一般的。

## 3. tfstate 用バケットはプロジェクトごとに分ける

- **決定**: `platform-tfstate` と `<project>-tfstate` を分ける。
- **理由**: 各プロジェクトの CI で terraform を実行するため、他のプロジェクトの state を読めないように厳密に分けたい。R2 の通常のトークンはバケット単位でしか権限を絞れない。バケットの作成は platform で自動化するので、分けても手間は増えない。
- **補足**: ロックは state ファイルごとなので、1つのバケットにまとめてもロックの問題はない。分ける理由はあくまで権限。
- **限界**: この分離が効くのは、state バケット用の R2 キーを使った直接のアクセスだけ。R2 の Admin 権限を持つプロジェクトや、Worker のバインディングを使うプロジェクトは、他のプロジェクトの state バケットにも届く。これは受け入れる（[10](#10-r2-バケットの作り分け)、[11](#11-プロジェクト同士はバインディングで筒抜けになることを受け入れる)）。

## 4. platform も GitHub Actions で apply する

- **決定**: 手元では terraform を実行せず、AI が PR を作り、自分が plan を確認してマージする。
- **理由**: 手元での作業を減らしたい。AI に任せやすくしたい。
- **対策**: 一番強い鍵を CI に置くことになるので、AI の書いたコードが鍵に触れる経路を塞ぐ（[workflow](workflow.md)）。

## 5. platform リポジトリは公開する

- **決定**: 公開リポジトリにする。
- **理由**: GitHub Free の非公開リポジトリでは Environments（環境ごとのシークレット、使えるブランチの制限）が使えず、どのブランチのワークフローからでも鍵を読めてしまう。公開リポジトリなら Environments と required reviewers が無料で使える。構成が見えても困らない。
- **対策**: 個人情報や秘密をコードやログに出さない。シークレットスキャンを有効にする。`/plan` はオーナーのコメントだけで動かし、フォークの PR は plan しない。

## 6. GitHub リポジトリも platform で管理する

- **決定**: プロジェクトのリポジトリ自体を platform で作る。
- **理由**: リポジトリが先にないと Secrets を書き込めない。プロジェクトを始めるときに、1つの PR で土台がすべて揃うようにしたい。
- **対策**: PAT がリポジトリを削除できる権限を持つので、`archive_on_destroy = true` と `prevent_destroy` を必ず付ける。

## 7. platform リポジトリ自身の設定は管理しない

- **決定**: platform 自身のブランチ保護や Environments は手動で設定する。
- **理由**: Terraform で管理すると、AI が保護を外す PR を出して、うっかりマージしてしまう経路ができる。

## 8. Cloudflare Access は共有部分だけ platform に置く

- **決定**: ログイン方法（IdP）、チームドメイン、使い回すポリシーは platform に、Access アプリケーションとアプリ専用のポリシーは各プロジェクトに置く。
- **理由**: Access アプリケーションは守るホスト名ごとに作るもので、プロジェクトに属する。

## 9. platform の state は別の Cloudflare アカウントに置く

- **決定**: `platform-tfstate` を、それ専用の Cloudflare アカウント（state アカウント）に置く。state アカウントは Terraform で管理せず、手動で作ったバケットと R2 キーだけを置く。
- **理由**: R2 のトークンでバケット単位に絞れるのはオブジェクトの読み書き権限だけで、バケットを作る Admin 権限はアカウント内の全バケットに効く。platform の state にはトークンの値が入っているので、同じアカウントに置くと、R2 の Admin 権限を持つプロジェクトが platform の state を読めて、実質的にすべての権限を持つことになる。権限の細かい組み合わせで防ぐより、アカウントという境界で切る方が確実。
- **対策**: プロジェクト用トークンは、メインアカウントのアカウントトークンとして発行し、state アカウントに構造的に届かないようにする。Cloudflare のログインは2段階認証で守る。

## 10. R2 バケットの作り分け

- **決定**:
  - 各プロジェクトの tfstate 用バケット（`<project>-tfstate`）は platform が作る。置き場所はメインアカウント。
  - アプリのロジックが使うバケット（画像の保存先など）は、各プロジェクトが自分で作る。必要なプロジェクトには R2 の Admin 権限を渡してよい。
- **理由**:
  - tfstate 用バケットは、プロジェクトの Terraform を動かす前に必要なので、platform で用意するしかない。
  - アプリ用バケットは、Worker や D1 と同じくアプリの部品なので、アプリと一緒に管理する方が分かりやすい。
  - R2 の Admin 権限はアカウント内の全バケットに効くので、他のプロジェクトのバケットも見えるようになる。ただし、Worker のバインディング経由ではどのみち届くので（[11](#11-プロジェクト同士はバインディングで筒抜けになることを受け入れる)）、Admin 権限を渡しても増えるリスクは小さい。
- **プロジェクトの tfstate 用バケットを state アカウントに置かない理由**: platform がそこでバケットを作ったり R2 キーを発行したりするには、state アカウントを扱えるトークンを platform の CI に置く必要がある。そのトークンは `platform-tfstate` にも届くので、state アカウントを Terraform で触らないことによる守りが崩れる。
- **検討した別案**: アプリ用も含めて R2 バケットはすべて platform で作り、プロジェクトには R2 の Admin 権限を渡さない案。一度はこの方針にしたが、バインディングの検証で中身へのアクセスは防げないと分かり、効果に対してアプリの部品が platform に分散するデメリットの方が大きいと判断した。

## 11. プロジェクト同士はバインディングで筒抜けになることを受け入れる

- **検証結果（2026-11-27、wrangler 4.168.0）**: `Workers Scripts:Edit` だけを持つアカウントトークンで検証した。
  - `wrangler r2 bucket list` は認証エラーになった（R2 の権限は持っていない）。
  - それでも、別のバケットをバインディングした Worker をデプロイでき、そのバケットのオブジェクトを読み出せた。
  - つまり、**Worker をデプロイできるトークンなら、同じアカウント内のどの R2 バケットでも読み書きできる。** D1 や KV のバインディングも同様と考えておく（未検証）。
- **決定**: これを受け入れる。メインアカウントの中では、プロジェクト同士の state やデータは互いに届きうる前提で運用する。
- **理由**: 本当に守る必要があるのは、全トークンが入った platform の state で、それは別アカウントに置くこと（[9](#9-platform-の-state-は別の-cloudflare-アカウントに置く)）で守れている。プロジェクト側の state には強い秘密を置かないので、漏れても被害はそのプロジェクトのデータの範囲で収まる。プロジェクトごとにアカウントを分けたり、プロジェクトの state を別アカウントに移したりする案もあったが、個人用の規模では手間に見合わない。
- **運用でのカバー**:
  - プロジェクトの Worker がバインディングするのは、自分のプロジェクトのリソースだけにする。
  - 各プロジェクトの plan を確認するときに、バインディング先が自分のリソースになっているかを見る。
  - 強い秘密（API トークン、Access のサービストークン、Worker 用のシークレット、生成したパスワードなど）はプロジェクト側の state に置かず、platform で作って渡す。
  - トークンを作れる権限（`API Tokens Edit`、`Account API Tokens Edit` など）は、プロジェクトに渡さない。これを持つと、自分で強いトークンを作れてしまう。
